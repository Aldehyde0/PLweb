## 背景与问题 {#background}

:::field{path="background" type="paragraphs"}
工具参数如果只是自由文字，程序很难稳定区分路径、数量与可选条件。函数工具用结构化接口告诉模型可提交哪些字段，再由应用将合法请求交给实际函数实现。

Schema 能提前发现一部分结构错误，但它不认识业务世界：类型正确的路径可能越界，合法整数也可能超过额度。因此结构约束与执行前验证必须分层。
:::


## 概念定义 {#definition}

:::field{path="definition" type="paragraphs"}
函数工具是由名称、描述、输入参数 Schema 和执行实现构成的工具接口。
:::


## 直观理解 {#intuition}

:::field{path="intuition" type="paragraphs"}
它像一份机器可读表单：字段、类型、枚举和必填项都明确。
:::


## 核心原理 {#core-principle}

:::field{path="corePrinciple" type="paragraphs"}
名称与描述应说明函数用途、何时适用和返回什么。参数 Schema 则定义对象、字段类型、必填项与额外属性；嵌套对象也要按实际接口约束，避免模型插入执行器没有处理的字段。

下方示例使用 OpenAI 的 strict 函数模式：对象声明不接收额外属性，定义的字段列入 required；允许缺省语义的值用可包含 null 的类型表达。这里“字段必须出现”与“值不能为 null”是两件事。

执行器先做结构验证，再做语义验证。例如 max_chars 为整数并不代表负数有意义，path 为字符串并不代表它在授权根目录内；默认值、范围和资源权限仍需由实现明确处理。

返回值也应有稳定契约，区分内容、截断标记和失败原因。工具描述和 Schema 的修改相当于接口变化，调用者与实现要一起更新，并检查旧调用是否仍能正确处理。
:::


### 案例：一份笔记读取请求的三层检查

按下方 Schema，参数可以是路径为 `notes/agent.md`、max_chars 为 null 的对象；实现可以约定 null 使用默认长度。但遗漏 max_chars 或多出未声明字段，在严格结构约束下应被拒绝。

即使路径与类型都合法，`notes/../private.md` 仍需要解析后检查是否越过允许目录。max_chars 为负数也需要业务范围校验。最后，读取成功返回的内容是否支持用户问题，还属于任务验收层；这三层不能互相代替。

:::field{path="codeExamples.0.source" type="code" trailing="0"}
```JSON
{
  "type": "function",
  "name": "read_note",
  "description": "读取允许目录中的一份 Markdown 笔记",
  "strict": true,
  "parameters": {
    "type": "object",
    "properties": {
      "path": {"type": "string"},
      "max_chars": {"type": ["integer", "null"]}
    },
    "required": ["path", "max_chars"],
    "additionalProperties": false
  }
}
```
:::

:::field{path="codeExamples.0.explanation" type="list"}
- type 和 name 标识函数工具。
- parameters 使用 JSON Schema；strict\:true 要求完整且封闭的对象结构。
- max\_chars 用 null 表达可选语义，但仍位于 required。
:::

## 常见错误 {#pitfalls}

:::field{path="pitfalls" type="list"}
- 描述过于模糊，多个函数用途重叠，模型无法判断什么时候选哪一个。
- 在本页严格模式示例中只删除 required 字段来表达可选性，或忘记关闭额外属性。
- 把结构验证当作资源授权、数值范围检查或最终结果正确性的证明。
:::

## 安全风险与信任边界 {#security-risks}

符合 JSON Schema 只证明参数结构满足约束，不证明收款人、路径或金额在业务上正确。函数返回的文本也可能包含外部指令，应作为数据解析；会改变外部状态的函数还需区分提交成功、结果未知与明确失败。

## 性能与失败模式 {#performance-notes}

调用耗时通常包括模型选函数、参数校验、执行和结果回传，失败重试会扩大尾部延迟。测试应分别检查选函数是否正确、参数语义是否正确与最终结果是否达成；存在依赖的函数不能只为降延迟而并行。
