## 背景与问题 {#background}

:::field{path="background" type="paragraphs"}
Agent、Skill、Tool 与 MCP 经常一起出现，但它们解决的层次不同。混淆后容易出现两类错误：以为安装了一份流程说明就拥有执行能力，或以为接通协议就已经得到会自主完成任务的系统。

辨别时可以沿一次任务追问：谁决定下一步，依据什么流程，什么实现真正执行动作，外部能力通过什么接口连接。产品名称可能把多种能力打包，但职责仍然需要区分。
:::


## 概念定义 {#definition}

:::field{path="definition" type="paragraphs"}
Agent 组织目标与行动；Skill 提供可复用流程和专业规范；Tool 执行具体动作；MCP 以协议连接 Client 与外部能力。
:::


## 直观理解 {#intuition}

:::field{path="intuition" type="paragraphs"}
读取本地 PDF 时：模型理解意图，Agent 安排任务，Skill 规定阅读和总结流程，PDF Tool 读取文件，MCP 可把外部文件服务统一提供给 Agent。
:::


## 核心原理 {#core-principle}

:::field{path="corePrinciple" type="paragraphs"}
Agent 维护目标与运行状态，决定何时调用能力并判断结果。模型只是其中的决策组件，运行器还需要处理执行、权限、反馈和停止。

Skill 提供可复用的方法、约束、参考资料或辅助脚本，告诉系统如何处理一类任务。它可以指导调用工具，但并不因为说明里写了某个动作，就自动拥有该动作的权限或服务连接。

Tool 是可被运行器调用的具体能力，例如读取文件、执行计算或请求业务服务。工具契约描述参数和返回值；真正的实现与执行环境负责产生结果，Schema 通过仍要检查业务权限。

MCP 标准化宿主中的 Client 与外部 Server 如何发现和调用工具、资源及 Prompt。它解决连接与协议问题，不替代业务实现，也不替 Agent 作决策。Plugin 等产品打包形式可能同时包含 Skill、工具和连接配置，应看实际内容而不是名称推断边界。
:::


### 案例：一次本地报表审阅中的四层分工

用户要求审阅报表。Agent 维护审阅进度；报表审阅 Skill 提供先核数据口径、再查异常和引用证据的流程；读取表格与计算汇总是具体 Tool。如果表格位于独立服务中，MCP 可以承担工具发现与调用的协议连接。

若只有 Skill 而没有读取能力，系统无法凭说明获得表格内容；若只有 MCP Server 而没有任务控制，也不会自行决定审阅哪些字段。即使四层都齐备，发布修改仍需要相应权限。这套拆解可以帮助定位缺的是流程知识、执行实现、连接还是任务控制。

## 常见错误 {#pitfalls}

:::field{path="pitfalls" type="list"}
- 把 Skill 目录等同于可执行 API，认为安装说明文件就完成服务集成。
- 把 MCP Server 当作自主 Agent，或者把协议连接成功当成工具调用已获授权。
- 因产品同时打包多种能力就把术语视为同义词，无法解释真实执行与信任边界。
:::

## 安全风险与信任边界 {#security-risks}

Skill 提供的说明、工具暴露的能力与 MCP 建立的连接，分别处于不同层次。安装说明或发现工具不等于其中每个动作都适合当前任务；服务端描述及返回内容仍需按来源处理，不能因使用统一协议就当成可信指令。

## 性能与失败模式 {#performance-notes}

选型应先看缺少的是工作方法、可执行能力还是跨服务连接。额外说明会占用上下文，更多工具会增加选择难度，远程服务还引入往返与启动成本；协议统一能改善集成，但不能直接证明模型效果或运行速度提升。
