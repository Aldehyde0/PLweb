## 背景与问题 {#background}

:::field{path="background" type="paragraphs"}
AI 应用连接文件、数据库和业务服务时，如果每个宿主都维护一套专有的能力发现与调用格式，集成和迁移会越来越复杂。MCP 为宿主和能力提供方建立共同协议，让双方先在接口层使用同一种语言。

协议统一不代表业务自动统一。不同服务仍有不同的数据含义、权限和错误条件，宿主也仍需决定哪些能力适合当前用户与任务。
:::


## 概念定义 {#definition}

:::field{path="definition" type="paragraphs"}
MCP 全称 Model Context Protocol。它规定 Client 与 Server 如何发现和调用能力，不等同于某个具体工具、API 或 Agent。
:::


## 直观理解 {#intuition}

:::field{path="intuition" type="paragraphs"}
MCP 像通用插座规范：Server 提供插口后的工具与资料，Client 负责连接，Agent 决定何时使用；插座本身不替你完成任务。
:::


## 核心原理 {#core-principle}

:::field{path="corePrinciple" type="paragraphs"}
MCP 采用 Host、Client 与 Server 分工：Host 管理 AI 应用与用户交互，Client 负责对接某个 Server，Server 暴露具体能力。Agent 可以利用这些能力推进任务，但 MCP 本身不是负责目标与规划的 Agent。

Server 可以提供 Tools、Resources 与 Prompts。Tool 表示可执行能力，Resource 提供可读取的上下文，Prompt 提供可参数化的交互模板；它们不能都简化成“远程函数”。宿主决定如何把发现的内容呈现给模型或用户。

Client 通过协议发现能力、发送请求并关联结果，宿主再过滤工具、执行审批和验证输出。普通 API 定义某个业务服务的操作，MCP 可以将这些操作包装成面向 AI 应用的统一发现与调用接口；它不会取代业务实现。

协议行为需要注明版本。2026-07-28 规范以自包含请求携带版本与客户端能力，Server 可通过 server/discover 提供能力发现；旧版本采用连接级初始化。不能把旧教程中的 initialize 握手视为所有版本都必须执行的固定前提。

版本与职责可对照 [MCP 官方架构](https://modelcontextprotocol.io/specification/2026-07-28/architecture)。
:::


### 案例：两个宿主复用同一个知识服务

知识服务通过 MCP 提供文档检索 Tool、政策文档 Resource 和一份审阅 Prompt。桌面助手可以用 Tool 找片段，再读取 Resource；另一个支持相应 MCP 功能的编辑器也可按协议接入，而不必复制完全不同的私有调用格式。

两个宿主仍可能暴露不同的能力子集。只获检索授权的用户不能因为 Server 同时提供更新工具就自动修改知识库；某宿主不支持某种内容类型时也需要适配。复用的是协议与能力描述，任务流程、授权和效果验收仍由各应用落实。

## 理解与实践步骤 {#algorithm-steps}

:::field{path="algorithmSteps" type="ordered"}
1. 用户任务进入 Agent
2. Agent 查看 Client 暴露的允许能力
3. MCP Client 与 Server 协商并发现能力
4. Agent 选择 Tool 或请求 Resource
5. Client 发送协议请求
6. Server 执行并返回结构化结果
7. Agent 验证结果并继续或完成
:::

## 常见错误 {#pitfalls}

:::field{path="pitfalls" type="list"}
- 把接通 MCP 当成已经获得自主 Agent、业务权限或完整的任务流程。
- 默认信任 Server 的所有能力与返回内容，不做过滤和结果验证。
- 混用不同协议版本的初始化、元数据和传输示例，却不检查实际 SDK 与 Server 支持范围。
:::

## 安全风险与信任边界 {#security-risks}

MCP 统一连接和能力暴露方式，不会自动证明服务端可信、工具结果正确或执行环境已隔离。外部资源与服务响应仍是有来源的数据；工具发现后还要核对它操作的对象、实际副作用和当前任务是否需要这些能力。

## 性能与失败模式 {#performance-notes}

协议本身不决定模型质量。实际成本包括能力列表占用的上下文、连接启动、网络往返与后端工具耗时；应按完整任务比较调用成功、结果正确性和恢复能力，避免把“接口统一”直接解释为速度或准确率提升。
