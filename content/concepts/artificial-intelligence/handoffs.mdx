## 背景与问题 {#background}

:::field{path="background" type="paragraphs"}
有些场景需要专家直接接着与用户沟通。例如客服已经确认问题属于账单领域，继续由前台中转每一轮问答会增加延迟，还可能遗漏专家需要追问的信息。

Handoff 解决的是活动对话由谁继续处理的问题。它不同于请求专家分析一小段材料后返回主管，因此交接前必须明确目标、上下文和权限是否适合新的处理者。
:::


## 概念定义 {#definition}

:::field{path="definition" type="paragraphs"}
在 OpenAI Agents SDK 中，Handoff 作为模型可见的类函数工具，但调用后进入专门的交接路径，由目标 Agent 接管后续对话。
:::


## 直观理解 {#intuition}

:::field{path="intuition" type="paragraphs"}
前台确认问题类型后把电话真正转给专家，而不是每句话都通过前台中转。
:::


## 核心原理 {#core-principle}

:::field{path="corePrinciple" type="paragraphs"}
在 OpenAI Agents SDK 中，交接以模型可见的类函数能力暴露；被选中后，运行器进入专门交接路径，由指定目标 Agent 继续当前运行。普通专家工具返回后仍由调用者处理，二者控制流不同。

交接参数可以携带问题类别或简短移交说明等元数据。它不是整个应用上下文，也不会凭参数随意选择另一个目标；目标由应用配置的交接对象决定。

会话历史应按需要过滤，避免把无关私人信息传给新专家；同时保留目标、已验证事实、用户已给出的答案和未解决问题。只给一句含糊摘要可能迫使用户重复输入，也可能丢失原有约束。

若交接涉及不同账户、权限或领域，应用应在任何副作用前重新校验。SDK 的交接回调成功返回后会继续转移，授权失败不能只写一条警告然后正常返回；还要防止专家间来回转接形成循环。

这些控制流与输入参数的区分可对照 [Agents SDK 的 Handoff 文档](https://openai.github.io/openai-agents-js/guides/handoffs/)。
:::


### 案例：客服将账单争议交给账单专家

前台已收集订单标识和用户对重复扣款的描述，交接时传入“疑似重复扣款”的分类元数据，并保留已经核验的订单信息。专家接管后可以直接询问缺失的扣款记录，而不要求用户重新讲述整个问题。

历史中与另一个售后问题相关的地址信息可以过滤，访问账单的权限则必须由系统另外检查。交给账单专家不意味着批准退款；若需要退款，该副作用仍走明确授权与执行验证。用户收到的最终答复来自当前活动专家，而不是假定前台一定再收回汇总。

```TypeScript
import { Agent, run } from '@openai/agents';

const chineseAgent = new Agent({
  name: 'Chinese specialist',
  instructions: 'Reply in Chinese and keep technical terms precise.',
});

const englishAgent = new Agent({
  name: 'English specialist',
  instructions: 'Reply in English.',
});

const triageAgent = new Agent({
  name: 'Language triage',
  instructions: 'Hand off to the specialist matching the user language.',
  handoffs: [chineseAgent, englishAgent],
});

const result = await run(triageAgent, '请解释 Handoff。');
console.log(result.finalOutput);
```
:::

:::field{path="codeExamples.0.explanation" type="list"}

- triageAgent 的 handoffs 声明可交接目标。
- run 内部处理模型调用、交接与后续 Agent 循环；最终输出来自接管后的 Agent。
:::

## 常见错误 {#pitfalls}

:::field{path="pitfalls" type="list"}
- 把交接当成普通专家工具调用，错误预期会自动返回主管继续汇总。
- 把交接元数据当作完整上下文，或把全部历史未经筛选传给所有专家。
- 在交接回调中发现未授权却只记录日志后返回，或者让专家无限互相转接。
:::

## 安全风险与信任边界 {#security-risks}

移交应传递当前目标、已完成动作和必要证据，避免把整个历史中的敏感内容无差别复制。接收者需区分未执行计划与已发生副作用，不能将移交摘要中未经验证的结论升级为事实。

## 性能与失败模式 {#performance-notes}

移交会增加上下文重建与角色切换成本，也可能丢失约束。记录移交原因、去向与终止状态，检测重复转交和来回循环；评价要看移交后是否真正完成任务，而不只看路由是否成功。
